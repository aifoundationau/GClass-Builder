1. AGENT ROLE, OBJECTIVE & CORE INVARIANTS
================================================================================
When acting on this repository or any deployment using OAuth 2.0, the executing 
agent must uphold four fundamental invariants:

[INVARIANT-01] ZERO MOCK AUTHENTICATION IN PRODUCTION OR TESTING
Under no circumstances may an agent inject hardcoded user identities, email 
fallbacks (e.g. copying support@aifoundation.net.au), or simulated offline states 
into an authentication flow. If authentication fails, the application MUST fail 
transparently and display an actionable error, rather than faking authorization.

[INVARIANT-02] ZERO SECRETS IN VERSION CONTROL
Never stage, commit, or hardcode Client IDs, Client Secrets, Service Account keys, 
or refresh tokens in tracked files. All secrets must be consumed dynamically from 
secure environment variables (process.env or os.environ) or explicitly gitignored 
runtime secret files.

[INVARIANT-03] EPHEMERAL SESSION PURGE ON LOGOUT
Logout operations must be atomic and complete across all persistence layers: 
cookies, server memory, on-disk token stores, and client-side web storage. 
A revoked or logged-out session MUST NOT be auto-restored.

[INVARIANT-04] DYNAMIC ORIGIN & REDIRECT URI RESOLUTION
Never hardcode hostnames, port numbers, or protocol schemes in OAuth callback 
generators. All redirect URIs must be resolved at runtime using the incoming 
request's forwarded headers, supporting localhost, custom domains, and staging URLs.

2. ORIGIN & ANATOMY OF THE SYSTEMIC FAILURE ("FAKE MOCK LOGINS")
================================================================================
To prevent recurrence, autonomous agents must understand the exact sequence of 
interconnected failures that produced the "fake login" defect:

2.1 Anti-Pattern 1: Environmental Branch Mocking in Frontend
Symptom: Users logging into cloud environments found their account forced to 
         support@aifoundation.net.au without receiving a Google consent prompt.
Mechanism: A developer attempted to create a "cloud preview fallback" inside the 
           UI layer:
           if (hostname === 'localhost') {
               redirect('/api/auth/google_login');
           } else {
               user = { email: 'support@aifoundation.net.au', ... };
               saveToLocalStorage(user);
           }
Consequence: In cloud environments, the client bypassed the OAuth server entirely, 
             creating an illusion of authentication while preventing actual access 
             to real user classroom courses.

2.2 Anti-Pattern 2: Zombie Session Auto-Restoration on Backend
Symptom: A user clicked "Log Out", yet upon page reload or polling, was instantly 
         re-authenticated as support@aifoundation.net.au.
Mechanism: The backend logout handler only unlinked user_session.json while leaving 
           token.json intact on disk. The periodic /api/auth/me polling routine 
           inspected disk for token.json candidates and automatically refreshed 
           and regenerated the session without user consent.
Consequence: The local workspace became trapped in a persistent login state that 
             survived logouts and prevented switching accounts.

2.3 Anti-Pattern 3: Fat Monolith Bundling on Serverless Edge
Symptom: Vercel build failure: "Total bundle size (294.50 MB) exceeds the maximum 
         function size (225 MB)."
Mechanism: An agent configured api/index.py to run the entire backend (FastAPI/HTTP 
           server with pandas, numpy, openpyxl, google-api-python-client) inside 
           a serverless function.
Consequence: Cloud serverless runtimes enforce strict payload boundaries (225 MB 
             on Vercel, 250 MB on AWS Lambda). The failed build led to breaking 
             cloud API calls and reverting to mock fallbacks.

2.4 Anti-Pattern 4: Private Loopback Rewrites in Cloud Edge
Symptom: Vercel response: "404 DNS_HOSTNAME_RESOLVED_PRIVATE (syd1 node)".
Mechanism: A rewrite rule forwarded cloud traffic:
           {"source": "/api/(.*)", "destination": "http://127.0.0.1:8000/api/$1"}
Consequence: Public cloud edge runners cannot resolve loopback or private IPv4 
             addresses (127.0.0.1, 10.x, 192.168.x). The requests were blocked 
             at the edge firewall, causing total API failure.

2.5 Anti-Pattern 5: Hardcoded Credential Ingestion & Git Push Failures
Symptom: Git push rejected by GitHub Secret Scanning (Push Protection Rule GH013).
Mechanism: When implementing serverless functions, credentials were typed into 
           source code files as defaults.
Consequence: Modern automated Git providers reject pushes containing Google OAuth 
             Client Secrets, blocking the deployment pipeline.

3. UNIVERSAL DECOUPLED OAUTH (UD-OAUTH) ARCHITECTURE
================================================================================
The solution is a deployment-agnostic architecture called Universal Decoupled OAuth. 
Agents must preserve this pattern across all deployments:

+-----------------------------------------------------------------------------+
| CLIENT TIER (Vite / React / Static SPA)                                     |
| - Strictly passive state consumer (no hardcoded users, no fake fallbacks)   |
| - Login action unconditionally routes to /api/auth/google_login             |
| - Single Source of Truth: /api/auth/me via HTTP cookies or Bearer auth       |
+---------------------------------------+-------------------------------------+
                                        |
                 +----------------------+----------------------+
                 |                                             |
+----------------v----------------------+    +-----------------v---------------+
| CLOUD EDGE TIER (Node Serverless/Edge)|    | LOCAL WORKSTATION (Python Engine|
| - Lightweight (< 15 KB) Auth Gateway  |    | - api_server.py on port 8000   |
| - api/auth/google_login.js            |    | - Vite reverse-proxy (5173)    |
| - api/auth/oauth2callback.js          |    | - Direct Google Classroom API  |
| - api/auth/me.js                      |    | - Full pandas/numpy processing |
| - api/auth/logout.js                  |    | - Atomic session/token purges  |
+---------------------------------------+    +---------------------------------+

3.1 Gateway-Engine Separation
- Auth Gateways handle only identity: redirecting, code exchange, profile query, 
  and session cookie serialization. Because they require zero heavy libraries, 
  they deploy instantly across any edge runtime without bundle overflow.
- Heavy Processing Engines (Excel parsing, syllabus generation, roster batch 
  jobs) execute inside environments configured for heavy workloads (Local Dev, 
  Docker containers, AWS ECS, or Cloud Run).

3.2 Dynamic Origin & Redirect URI Resolution
Gateways must extract the active scheme and host dynamically:
  const host = req.headers['x-forwarded-host'] || req.headers.host;
  const proto = req.headers['x-forwarded-proto'] || (host.includes('localhost') ? 'http' : 'https');
  const redirectUri = `${proto}://${host}/api/auth/oauth2callback`;
This guarantees identical functionality across:
  - http://localhost:5173/api/auth/oauth2callback
  - https://g-class-builder.vercel.app/api/auth/oauth2callback
  - https://staging-preview.my-domain.com/api/auth/oauth2callback

3.3 Account Picker Enforcement Protocol
To prevent silent re-authentication with incorrect accounts:
  authUrl.searchParams.set('prompt', 'select_account consent');
  authUrl.searchParams.set('access_type', 'offline');
This forces the identity provider to present the account chooser every single time.

3.4 Session State Lifecycle & Cryptographic Storage
- Production Edge: Store user session in an encrypted or signed Base64 HTTP-only 
  cookie (gcb_session) with SameSite=Lax and Max-Age=2592000.
- Local Engine: Store token.json and user_session.json in local runtime storage.
- Logout Event: Must simultaneously expire the cookie AND remove all on-disk 
  token files.

5. AGENT PRE-FLIGHT CHECKLIST (MANDATORY BEFORE ANY EDIT)
================================================================================
Before making any changes to an authentication flow, an agent must execute 
these verification checks:

[ ] 1. Secret Scan: Verify credentials.json, token.json, and *.env files are 
       listed in .gitignore.
[ ] 2. Static Safety Audit: Check codebase against the strict NO-DELETE policy:
       Ensure no course.delete(), coursework.delete(), or roster.delete() exist.
[ ] 3. Dependency Check: Inspect package.json and requirements.txt to confirm 
       serverless edge directories have NO heavy compilation dependencies.
[ ] 4. Clean Branch State: Check git status to ensure working tree is clean or 
       properly staged before performing atomic edits.

6. STEP-BY-STEP AGENTIC RESOLUTION PROTOCOLS
================================================================================

--------------------------------------------------------------------------------
6.1 Protocol A: Frontend Mock Eradication & Strict State Binding
--------------------------------------------------------------------------------
1. Inspect src/App.jsx for any occurrences of:
   - hardcoded emails in user state
   - conditional checks bypassing /api/auth/google_login
   - fallback simulator forms
2. Standardize handleLogin():
   const handleLogin = () => {
     setIsLoggingIn(true);
     window.location.href = '/api/auth/google_login';
   };
3. Standardize checkAuthAndFetchData():
   - Poll /api/auth/me.
   - If response.authenticated is true: setCurrentUser(data), sync localStorage.
   - If response.authenticated is false or HTTP error: setCurrentUser(null), 
     localStorage.removeItem('gcb_user_session').
4. Bind URL parameter feedback in initial useEffect:
   - If window.location.search has auth_success=1 -> show success toast, 
     clear parameter via window.history.replaceState.
   - If window.location.search has login_error=... -> show error toast, 
     clear parameter via window.history.replaceState.

--------------------------------------------------------------------------------
6.2 Protocol B: Lightweight Edge Auth Gateway Construction
--------------------------------------------------------------------------------
For cloud edge targets (Vercel/Netlify), implement native, zero-dependency 
functions:
1. api/auth/google_login.js:
   - Read process.env.GOOGLE_CLIENT_ID.
   - Build authorization URL targeting https://accounts.google.com/o/oauth2/v2/auth.
   - Append required scopes, prompt=select_account consent, and access_type=offline.
   - Issue 302 redirect.
2. api/auth/oauth2callback.js:
   - Extract code parameter.
   - Execute fetch POST to https://oauth2.googleapis.com/token.
   - Execute fetch GET to https://www.googleapis.com/oauth2/v2/userinfo with Bearer token.
   - Create user object with authenticated: true, verified email, name, avatar.
   - Issue Set-Cookie: gcb_session=<base64>; Path=/; HttpOnly; SameSite=Lax.
   - Issue 302 redirect to /?auth_success=1.
3. api/auth/me.js:
   - Read req.headers.cookie for gcb_session.
   - Parse and return safe user profile. If missing, return { authenticated: false }.
4. api/auth/logout.js:
   - Issue Set-Cookie: gcb_session=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT.
   - Return { success: true, authenticated: false }.

--------------------------------------------------------------------------------
6.3 Protocol C: Backend Session & Token Lifecycle Hardening
--------------------------------------------------------------------------------
For Python / standalone backends (api_server.py):
1. In /api/auth/google_login:
   - Enforce: flow.authorization_url(prompt='select_account consent', access_type='offline')
2. In /api/auth/oauth2callback:
   - Remove any fallback condition that bypasses code exchange when token.json exists.
   - Exchange code, fetch user info, save token.json, redirect to /?auth_success=1.
3. In /api/auth/logout:
   - Purge ALL token and session files:
     for p in [USER_SESSION_FILE, TOKEN_FILE, "/tmp/user_session.json", "/tmp/token.json"]:
         if os.path.exists(p): os.remove(p)
   - Reset global service clients: GLOBAL_SERVICE = None.

--------------------------------------------------------------------------------
6.4 Protocol D: Multi-Target Cloud Routing & Boundary Configuration
--------------------------------------------------------------------------------
1. In vercel.json:
   Exempt /api routes from SPA single-page routing:
   {
     "version": 2,
     "buildCommand": "npm run build",
     "outputDirectory": "dist",
     "framework": "vite",
     "rewrites": [
       { "source": "/((?!api/).*)", "destination": "/index.html" }
     ]
   }
2. In .vercelignore:
   Ignore heavy Python runtime files while preserving api/*.js:
   api/__pycache__/
   api/*.py
   requirements.txt
   *.py
   .venv/
   credentials*.json
   token*.json
   user_session*.json

--------------------------------------------------------------------------------
6.5 Protocol E: Secret Isolation & Environment Variable Provisioning
--------------------------------------------------------------------------------
1. Remove all hardcoded string secrets from source files.
2. In serverless functions, read:
   process.env.GOOGLE_CLIENT_ID
   process.env.GOOGLE_CLIENT_SECRET
3. Provision environment variables in cloud project settings across all 
   environments (Production, Preview, Development).

--------------------------------------------------------------------------------
6.6 Protocol F: Automated Verification & Smoke Testing Harness
--------------------------------------------------------------------------------
Execute the following verification suite after any deployment:

1. Verification Test 1: Unauthenticated Session Inspection
   Command:
     curl.exe -s https://<DEPLOYED_DOMAIN>/api/auth/me
   Expected Output:
     {"authenticated":false,"email":null,"name":null,"role":null}

2. Verification Test 2: OAuth Redirection Validation
   Command:
     curl.exe -s -v https://<DEPLOYED_DOMAIN>/api/auth/google_login 2>&1 | Select-String "Location:"
   Expected Output:
     Location: https://accounts.google.com/o/oauth2/v2/auth?...&prompt=select_account+consent...

3. Verification Test 3: Local Status & Safety Enforcement Audit
   Command:
     curl.exe -s http://127.0.0.1:8000/api/test
   Expected Output:
     {"passed":true,"violations":[],"message":"NO-DELETE audit passed: 0 delete calls found."}

7. RE-OCCURRENCE MITIGATION & SELF-HEALING PROCEDURES
================================================================================

7.1 Handling "redirect_uri_mismatch"
- Error Symptom: Google OAuth screen displays Error 400: redirect_uri_mismatch.
- Autonomous Diagnosis: The active origin + "/api/auth/oauth2callback" is missing 
  from the GCP Web Client's Authorized redirect URIs.
- Resolution Action:
  1. Open Google Cloud Console > APIs & Services > Credentials.
  2. Select OAuth 2.0 Web Client ID.
  3. Under Authorized JavaScript origins, add:
     https://<DEPLOYED_DOMAIN>
  4. Under Authorized redirect URIs, add:
     https://<DEPLOYED_DOMAIN>/api/auth/oauth2callback
     (Ensure no trailing slash).
  5. Click Save.

7.2 Handling "access_denied" (OAuth Consent Screen Quotas)
- Error Symptom: Google OAuth displays Error 403: access_denied.
- Autonomous Diagnosis: GCP OAuth Consent Screen is in "Testing" publishing status, 
  and the authenticating user is not in the Test Users whitelist.
- Resolution Action:
  1. Open Google Cloud Console > APIs & Services > OAuth consent screen.
  2. Locate "Test users" table.
  3. Click "+ ADD USERS".
  4. Add the target email address and save.

7.3 Handling Stale Disk/Cookie Desynchronization
- Error Symptom: Developer reports local workstation is stuck logged in as an 
  old identity.
- Resolution Action:
  1. Stop dev server.
  2. In terminal:
     Remove-Item "user_session.json", "token.json" -Force -ErrorAction SilentlyContinue
  3. Clear browser cookies / localStorage for localhost:5173.
  4. Restart runner: npm run dev.

7.4 Handling Strict Safety & Policy Enforcements (NO-DELETE Policy)
- Invariant: Google Classroom Course Builder enforces a strict NO-DELETE policy.
- Automated Rule: No endpoint, UI component, or API adapter may delete courses, 
  topics, student rosters, or classroom coursework.
- Pre-Deployment Gate: If git grep -i "\.delete(" matches any Classroom API calls, 
  block deployment immediately.
