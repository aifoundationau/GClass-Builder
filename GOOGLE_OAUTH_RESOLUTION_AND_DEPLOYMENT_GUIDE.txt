1. EXECUTIVE SUMMARY
================================================================================
This document records the exact root cause, complete sequence of engineering 
steps taken, and standard operating procedures (SOP) established to resolve the 
issue where the application performed "fake logins" by copying 
support@aifoundation.net.au into state rather than authenticating against real 
Google accounts.

The application now operates on a hybrid dual-environment OAuth architecture:
- Locally: Vite (port 5173) proxies to Python (api_server.py, port 8000), 
  handling Google OAuth with dynamic origin detection and prompt='select_account consent'.
- On Vercel Cloud: Native Node.js Serverless Functions in api/auth/ execute 
  direct OAuth 2.0 token exchanges with Google and establish secure HTTP-only 
  session cookies (gcb_session), entirely bypassing Vercel's 225 MB Python limits.

================================================================================
2. ORIGIN AND ROOT CAUSE OF THE ISSUE ("FAKE LOGINS")
================================================================================
The issue of "fake logins copying support@aifoundation.net.au without real 
authentication" arose from an accumulation of five distinct technical causes:

--------------------------------------------------------------------------------
2.1 Frontend Hardcoded Mock Fallback
--------------------------------------------------------------------------------
In src/App.jsx, the function handleLogin() contained a hostname condition:
   if (window.location.hostname === 'localhost' || window.location.hostname === '127.0.0.1') {
       window.location.href = '/api/auth/google_login';
   } else {
       // Hosted Vercel cloud preview fallback
       const googleUser = {
           authenticated: true,
           email: "support@aifoundation.net.au",
           name: "AI Foundation Instructor",
           ...
       };
       setCurrentUser(googleUser);
       localStorage.setItem("gcb_user_session", JSON.stringify(googleUser));
   }
Whenever the user accessed the website on Vercel (https://g-class-builder.vercel.app),
the hostname was not localhost. Therefore, clicking "Sign in with Google Classroom" 
never redirected to Google. Instead, it instantiated a fake user object and copied
support@aifoundation.net.au into localStorage.

Additionally, the UI had two legacy elements:
a) A "TEST IDENTITY SWITCH" block offering buttons to manually switch to 
   support@aifoundation.net.au.
b) An "Instant Sign In (Simulator Mode)" input defaulting to support@aifoundation.net.au.
c) In checkAuthAndFetchData(), the frontend was unconditionally restoring 
   whatever was in localStorage without verifying with the server if the user 
   was genuinely authenticated.

--------------------------------------------------------------------------------
2.2 Local Server Auto-Restore of Stale Tokens
--------------------------------------------------------------------------------
In the local backend (api_server.py):
a) get_current_user_session() had an auto-restore fallback that inspected 
   candidate token.json files on disk. If a token existed, it refreshed the 
   token and immediately re-authenticated the session without user action.
b) In /api/auth/logout, the endpoint deleted user_session.json, but left 
   token.json intact on disk. Within seconds, the frontend's 10-second polling 
   loop called /api/auth/me, which found token.json, re-created user_session.json, 
   and logged the user right back in as support@aifoundation.net.au.
c) In /api/auth/google_login, authorization_url was called with:
   prompt='consent' rather than prompt='select_account consent'.
   Without select_account, Google did not display the account picker, silently 
   reusing whichever Google account was active in the browser.

--------------------------------------------------------------------------------
2.3 The Vercel Python 225 MB Function Limit Dilemma
--------------------------------------------------------------------------------
When attempting to deploy the Python backend directly to Vercel via api/index.py, 
Vercel's Python builder installed requirements.txt (which included pandas, 
numpy, openpyxl, and google-api-python-client).
The combined bundle was 294.50 MB, which triggered a fatal Vercel build error:
"Total bundle size (294.50 MB) exceeds the maximum function size (225 MB)."
This had previously led to disabling the cloud API and creating the mock fallback.

--------------------------------------------------------------------------------
2.4 The Vercel Routing Collision (404 DNS_HOSTNAME_RESOLVED_PRIVATE)
--------------------------------------------------------------------------------
In earlier vercel.json configurations, rewrites attempted to forward:
/api/(.*) -> http://127.0.0.1:8000/api/$1
On Vercel edge nodes (e.g. syd1), loopback addresses (127.0.0.1, localhost) 
are strictly blocked for security, resulting in the error:
"404 DNS_HOSTNAME_RESOLVED_PRIVATE".

--------------------------------------------------------------------------------
2.5 GitHub Push Protection & Secret Scanning Rejection
--------------------------------------------------------------------------------
When implementing new serverless functions, hardcoding Google Client IDs or 
Secrets in any commit was immediately rejected by GitHub Push Protection 
(Rule GH013: "Push cannot contain secrets"). All OAuth credentials had to be 
dynamically sourced from secure environment variables.

3. STEP-BY-STEP RESOLUTION EXPLANATION (EVERY ACTION TAKEN)
================================================================================

--------------------------------------------------------------------------------
3.1 Step 1: Removal of All Mock & Simulator Code from the Frontend
--------------------------------------------------------------------------------
File: src/App.jsx
Actions:
- Rewrote handleLogin() to unconditionally trigger real authentication:
  const handleLogin = () => {
    setIsLoggingIn(true);
    window.location.href = '/api/auth/google_login';
  };
- Completely removed handleEmailLogin(), the "Simulator Mode" input field, and 
  the "TEST IDENTITY SWITCH" buttons.
- Updated checkAuthAndFetchData() so that /api/auth/me is the single source of truth:
  If the API returns authenticated: true, the state and localStorage are updated.
  If the API returns authenticated: false, state is set to null and localStorage 
  is wiped immediately.
- Added URL parameter inspection in useEffect:
  If ?auth_success=1 is present, shows a success toast and cleans the URL via 
  window.history.replaceState.
  If ?login_error=... is present, shows the error message in a toast.

--------------------------------------------------------------------------------
3.2 Step 2: Elimination of the Heavy Python Serverless Entrypoint
--------------------------------------------------------------------------------
File: api/index.py
Action:
- Deleted api/index.py from the repository.
- This prevented Vercel from attempting to install pandas/numpy/scipy or invoke 
  the Python build runtime, avoiding the 225 MB size limit entirely.

--------------------------------------------------------------------------------
3.3 Step 3: Architecture of Lightweight Node.js Serverless Functions for Vercel
--------------------------------------------------------------------------------
Files Created:
- api/auth/google_login.js:
  Dynamically reads host from x-forwarded-host or host header.
  Constructs redirectUri: `${proto}://${host}/api/auth/oauth2callback`.
  Attaches Classroom scopes:
  - https://www.googleapis.com/auth/classroom.courses
  - https://www.googleapis.com/auth/classroom.topics
  - https://www.googleapis.com/auth/classroom.coursework.students
  - https://www.googleapis.com/auth/classroom.courseworkmaterials
  - https://www.googleapis.com/auth/classroom.announcements
  - https://www.googleapis.com/auth/classroom.rosters.readonly
  - openid, https://www.googleapis.com/auth/userinfo.email, https://www.googleapis.com/auth/userinfo.profile
  Appends prompt='select_account consent' and access_type='offline'.
  Sends a 302 redirect directly to accounts.google.com.

- api/auth/oauth2callback.js:
  Extracts code from query parameters.
  Performs server-to-server POST to https://oauth2.googleapis.com/token.
  Queries https://www.googleapis.com/oauth2/v2/userinfo with the access token.
  Extracts genuine user details: email, name, avatar picture.
  Encodes user session into base64 and sets an HTTP-only cookie (gcb_session) 
  with SameSite=Lax and 30-day expiry.
  Sends a 302 redirect to /?auth_success=1.

- api/auth/me.js:
  Reads and decodes the gcb_session cookie.
  Returns { authenticated: true, email, name, avatar, role, domain }.
  If cookie is missing or invalid, returns { authenticated: false }.

- api/auth/logout.js:
  Clears the gcb_session cookie with an expired timestamp.
  Returns { success: true, authenticated: false }.

- api/status.js:
  Returns { status: "online", mode: "Live Google Classroom API", no_delete_policy_enforced: true }.

- api/courses.js:
  Inspects the user's access token in gcb_session and queries 
  https://classroom.googleapis.com/v1/courses for their active courses.

Bundle Size:
- Less than 15 KB total. Zero third-party dependencies (uses native Node.js fetch, 
  URLSearchParams, Buffer). Deploys in under 15 seconds.

--------------------------------------------------------------------------------
3.4 Step 4: Local Python Server Hardening (api_server.py)
--------------------------------------------------------------------------------
File: api_server.py
Actions:
- In /api/auth/google_login:
  Changed flow.authorization_url(prompt='consent') to:
  flow.authorization_url(prompt='select_account consent', access_type='offline')
  This forces the browser to prompt the user to choose their Google account.
- In /api/auth/oauth2callback:
  Removed the bypass condition that accepted missing codes if token.json existed.
  Redirects to /?auth_success=1 upon verified token exchange.
- In /api/auth/logout:
  Modified logout handler to delete both USER_SESSION_FILE and TOKEN_FILE 
  (along with all /tmp/token.json candidates), and set GLOBAL_SERVICE = None.
  This permanently prevents the server from auto-restoring an old session.

--------------------------------------------------------------------------------
3.5 Step 5: Vercel Routing Configuration (vercel.json & .vercelignore)
--------------------------------------------------------------------------------
File: vercel.json
- Modified rewrites to exclude /api routes from the single-page application index:
  "rewrites": [
    {
      "source": "/((?!api/).*)",
      "destination": "/index.html"
    }
  ]
  This ensures /api/auth/* is routed to serverless functions, while all other 
  routes load the Vite frontend.

File: .vercelignore
- Removed the broad "api/" ignore rule so Vercel includes api/*.js.
- Added precise ignore patterns for Python assets:
  api/__pycache__/
  api/*.py
  requirements.txt
  *.py
  *.xlsx
  .venv/
  credentials*.json
  token*.json
  user_session*.json

--------------------------------------------------------------------------------
3.6 Step 6: GitHub Secret Protection Compliance (Zero Hardcoded Secrets)
--------------------------------------------------------------------------------
Files: api/auth/google_login.js, api/auth/oauth2callback.js
- Removed hardcoded Client ID and Secret string literals.
- Sourced credentials via process.env.GOOGLE_CLIENT_ID and 
  process.env.GOOGLE_CLIENT_SECRET, with a safe fallback to local credentials.json 
  (which is strictly gitignored).
- Amended commit and pushed cleanly to remote main branch without secret leaks.

4. STANDARD OPERATING PROCEDURE (SOP): INSTRUCTIONS TO FOLLOW EVERY TIME THIS OCCURS
================================================================================

If authentication ever fails, displays an unexpected user, or returns an error, 
follow this exact checklist in sequence:

--------------------------------------------------------------------------------
4.1 Phase 1: Diagnosing the Symptom
--------------------------------------------------------------------------------
1. Check what the browser URL displays:
   - If the URL contains "?login_error=...", read the message.
   - If the error is "redirect_uri_mismatch", proceed to Phase 2.
   - If the error is "access_denied", proceed to Phase 3.
2. Check network requests in Browser DevTools (F12 > Network):
   - Click "Sign in with Google Classroom".
   - Confirm the first request goes to "/api/auth/google_login" and returns HTTP 302.
   - Inspect the "Location" response header. It MUST begin with "https://accounts.google.com/".
   - If it redirects to "/" or sets a simulated user, check src/App.jsx for any rogue mock code.

--------------------------------------------------------------------------------
4.2 Phase 2: Resolving Google Cloud Console "Error 400: redirect_uri_mismatch"
--------------------------------------------------------------------------------
Cause: The URL where Google sends the authorization code does not match the list 
       in Google Cloud Console character-for-character.

Fix:
1. Open Google Cloud Console:
   https://console.cloud.google.com/apis/credentials
2. Select your project (e.g. gen-lang-client-0551298781).
3. Click your OAuth 2.0 Client ID (Web application).
4. Verify Authorized JavaScript origins:
   http://localhost:5173
   http://127.0.0.1:5173
   https://g-class-builder.vercel.app
5. Verify Authorized redirect URIs:
   http://localhost:5173/api/auth/oauth2callback
   https://g-class-builder.vercel.app/api/auth/oauth2callback
   * CRITICAL: Do NOT add trailing slashes (e.g. no "/api/auth/oauth2callback/").
6. Click SAVE. Changes take effect within 60-120 seconds.

--------------------------------------------------------------------------------
4.3 Phase 3: Resolving "Error 403: access_denied" (Test User Limitation)
--------------------------------------------------------------------------------
Cause: While your Google Cloud OAuth Consent Screen is in "Testing" mode, Google 
       rejects any Google account that is not explicitly whitelisted.

Fix:
1. Open OAuth Consent Screen in Google Cloud Console:
   https://console.cloud.google.com/apis/credentials/consent
2. Scroll to "Test users".
3. Click "+ ADD USERS".
4. Enter the email address of every teacher, tester, or personal account needing access:
   - support@aifoundation.net.au
   - (your personal Gmail or work Google Workspace email)
5. Click SAVE.

--------------------------------------------------------------------------------
4.4 Phase 4: Local Environment Reset (Clearing Stale Tokens)
--------------------------------------------------------------------------------
If local development is stuck remembering an old session:
1. Stop the running dev runner:
   Run task manager or kill task in terminal.
2. Delete cached local token and session files:
   In PowerShell:
   Remove-Item -Path "user_session.json", "token.json" -Force -ErrorAction SilentlyContinue
3. Open browser DevTools on http://localhost:5173:
   Application > Storage > Clear Site Data (or clear localStorage and Cookies).
4. Restart the fullstack runner:
   npm run dev (or node dev-runner.mjs)
5. Visit http://localhost:5173. The top bar will show "Not Signed In".
6. Click "Sign in with Google Classroom" to authenticate cleanly.

--------------------------------------------------------------------------------
4.5 Phase 5: Vercel Environment Variables Verification
--------------------------------------------------------------------------------
If Vercel cloud returns "?login_error=GOOGLE_CLIENT_ID is not configured":
1. Open Vercel Project Settings:
   https://vercel.com/aifoundationau/g-class-builder/settings/environment-variables
2. Verify both variables exist across Production, Preview, and Development:
   - GOOGLE_CLIENT_ID:     (Set to your GCP Web Client ID, e.g., 102300054859-...apps.googleusercontent.com)
   - GOOGLE_CLIENT_SECRET: (Set to your GCP Client Secret, e.g., GOCSPX-...)
3. If added or updated, click "Deployments" > latest deployment > "Redeploy" to apply.

--------------------------------------------------------------------------------
4.6 Phase 6: Code Base Safety Audit (Enforcing the NO-DELETE Policy)
--------------------------------------------------------------------------------
Under AI Foundation policy, this codebase enforces a strict NO-DELETE policy 
across all Google Classroom API interactions.
To verify safety integrity before any deployment:
1. Run the safety audit endpoint:
   curl.exe http://127.0.0.1:8000/api/test
2. Output must show:
   {"passed": true, "violations": [], "message": "NO-DELETE audit passed: 0 delete calls found."}
3. Never introduce any calls to .delete() on courses, courseWork, courseWorkMaterials, 
   announcements, or rosters.
